# REVIEW.md

Defects found in the starter `app/main.py` (helpers and endpoints). Times below are IST, shift 09:30-18:30 unless stated.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | Module top: `MongoClient(os.getenv("MONGO_URI", "mongodb://localhost:27017"))`, `os.getenv("MONGO_DB", "attendance_db")` | Connection details are hard-coded as fallbacks. A missing variable silently connects to the wrong database instead of failing. | Unset `MONGO_DB`: the app starts happily and writes to `attendance_db`. | Read both from the environment (`load_dotenv(override=False)` so real env vars win) and fail fast if either is missing. |
| 2 | `MongoClient(...)` | No `tz_aware=True`, so PyMongo returns **naive** datetimes. Any later `.timestamp()` or IST conversion treats them as server-local time. | On a machine not set to UTC, a stored `03:58Z` punch comes back hours off. | `MongoClient(..., tz_aware=True, tzinfo=UTC)`. All instants in the code are aware UTC datetimes. |
| 3 | Startup (missing) | No indexes are created. There is no unique index on `employees.emp_code` or `attendance_logs(emp_code, date)`, so uniqueness depends on check-then-insert. Every list and analytics query runs a COLLSCAN. | Explain on `/attendance` shows `COLLSCAN`. Concurrent creates or punch-ins produce duplicates. | `ensure_indexes()` runs from the lifespan hook and is idempotent. It creates unique `emp_code`, unique `(emp_code, date)`, `(date desc, emp_code)`, `(status, date desc, emp_code)`, and indexes on employees by department and `joined_on`. |
| 4 | `health` | Always returns 200, even when MongoDB is down. | Stop mongod and `/health` still says ok. | Pings the server (`serverSelectionTimeoutMS=5000`) and returns 503 on failure. It also retries index creation if startup could not create them. |
| 5 | `compute_late_minutes` | `minutes > 10` compares already-truncated minutes, so 09:40:30 gives `int(10.5)=10`, then `10 > 10` is false and the result is 0. R2 says *strictly more than 10:00*, so the answer is 10. It does not truncate to seconds first. It uses `punch_in.replace(hour=...)` in whatever zone `punch_in` is in, which is server-local time from `fromtimestamp`. | Shift 09:30, punch 09:40:30 returns 0 (expected 10). The UTC-epoch input gives a different result on servers in different time zones. | Compare elapsed **seconds** `> 600`, then `seconds // 60`. Shift start is built in IST on the record's attendance date. |
| 6 | `compute_late_minutes` (overnight) | For a 22:00-06:00 shift, a 00:30 punch is measured against 22:00 of the *same* calendar day, so it comes out negative and late is 0. | Overnight employee punches 00:30 and gets late=0 (expected 150). | Shift start is anchored on the **attendance date** from R1, which is the previous day. |
| 7 | `compute_work_hours` | `round()` uses binary-float, round-half-even rounding instead of R4's half-up. Seconds are not truncated. | 1 h 0 m 18 s = 1.005 h: `round(1.005, 2)` gives 1.0, expected 1.01. | `Decimal(seconds)/3600` quantized with `ROUND_HALF_UP` on whole-second instants. |
| 8 | `compute_overtime` | Ignores the 30-minute minimum (R3): 5 minutes over returns 5. For overnight shifts the end is put on the *start* day, not the next day. It compares an IST-aware `end` with the naive `punch_out` the starter produces, which raises `TypeError` and returns a 500. | Punch-out 18:35 gives 5 (expected 0). Overnight 06:40 punch-out gives ~ +1000 min. Any naive input crashes. | Floor minutes from the correct shift-end instant (next day if overnight). Return the value only if it is `>= 30`, otherwise 0. |
| 9 | `EmployeeIn` | No validation: any `emp_code`, email, `HH:MM`, `joined_on`. `shift_start == shift_end` is accepted. Lax types (`"name": 5`). | `emp_code: "foo"`, `joined_on: "2026-02-30"`, `shift_start: "25:00"` all return 201. | Pydantic constraints from the contract (patterns, lengths, strict strings, real calendar date, `shift_start != shift_end`). |
| 10 | `PunchInIn` | `punched_at: Optional[int]` is lax: it accepts `"1783312500000"` (string), `1783312500000.0` (float), `true`, and seconds-looking values. `status: str` accepts `ABSENT`, `LEAVE`, or anything. | `punched_at: 1783312500` (seconds) creates a 1970 record. `status: "ABSENT"` is accepted at punch-in. | `StrictInt` with `ge=100000000000, le=4102444800000`, explicit `null` rejected, `status: Literal[PRESENT, WFH, ON_DUTY]`. |
| 11 | `create_employee` | Check-then-insert is racy: two concurrent creates both pass `find_one` and both insert. `created_at` is `datetime.now()` (naive, server-local) and is returned as a datetime, not epoch ms. | 10 parallel POSTs with the same code give several 201s. Response has `"created_at": "2026-..."`. | Insert directly and let the unique index decide (`DuplicateKeyError` gives 409). `created_at = now(UTC)`, serialized to epoch ms. |
| 12 | `list_employees` | `skip = page * page_size` skips the first page. `total` counts the whole collection, not the filter. No sort, so order is undefined. No bounds on `page` / `page_size` (page 0 gives a negative skip and a 500; page_size 10000 is allowed). | `?page=1` returns employees 21-40. `?department=Eng` reports the total of all departments. | `skip=(page-1)*page_size`, `count_documents(q)`, `.sort("emp_code")`, `Query(ge=1)` and `Query(ge=1, le=100)`. |
| 13 | `punch_in`, employee lookup | `emp` may be `None`, so `emp["shift_start"]` raises `TypeError` and returns 500 instead of 404. | Punch-in for `EMP9999` returns 500. | Shared `get_employee_or_404`. |
| 14 | `punch_in`, date | `datetime.fromtimestamp(ms/1000)` uses the server's local zone, so `date` is the server's calendar date, not IST. No truncation to seconds. The overnight rule in R1 is missing. `if body.punched_at` treats `0` as "now". | On a UTC server, a punch at 01:00 IST (19:30Z the day before) is filed under the previous day. An overnight 00:30 punch is filed under the wrong day. | `ms_to_dt` (integer maths, truncates to seconds, UTC-aware) and `attendance_date()` (IST date, overnight shift moved back one day). Uses `is not None`. |
| 15 | `punch_in`, uniqueness | Check-then-insert race: two simultaneous punch-ins both see no record and both insert. | 10 parallel punch-ins give more than one 201 and duplicate (emp_code, date) docs. | Unique `(emp_code, date)` index plus plain `insert_one`. The loser gets `DuplicateKeyError` and a 409. |
| 16 | `punch_in` / `list_attendance` responses | Leaks `id` (`str(_id)`), which the contract says never appears. Instants are returned as ISO datetimes, not epoch ms. Missing `history` / `half_day` on legacy docs are not defaulted. | Response has an `id` key and `"punch_in": "2026-07-06T..."`. Sample document 9 comes back without `half_day`. | `serialize_record()` builds exactly the contract fields: ms for `punch_in`/`punch_out`/`history.at`/`changes.*`, defaults `[]`/`false`/`0`. |
| 17 | `list_attendance`, scale | Loads the **entire** filtered collection into Python and sorts and paginates in memory. | At 100k docs it takes seconds and uses a lot of memory; explain shows COLLSCAN. | `find(q).sort(date desc, emp_code asc).skip().limit()` backed by the `(date desc, emp_code)` / `(emp_code, date)` / `(status, date desc, emp_code)` indexes. `count_documents(q)` for `total`. |
| 18 | `list_attendance`, contract | The sort has no `emp_code` tiebreak, so pages overlap or skip rows within a date. No validation: malformed dates, `date_from > date_to`, unknown `status`, `page=0`, `page_size>100` are all accepted (or return 500). | Two pages with the same date share or miss rows. `?date_from=2026-07-09&date_to=2026-07-01` returns 200 and nothing. | Secondary sort on `emp_code`. Dates are parsed strictly. `date_from > date_to` returns 422. `status` is an enum. Page bounds are enforced. |

### Looked at and decided were fine (or kept)
- **`IST = timezone(timedelta(hours=5, minutes=30))`.** Correct: India has no DST, so a fixed offset is right. I kept it.
- **`load_dotenv()`.** Its default is `override=False`, so real environment variables already win. I made that explicit.
- **Sync (`def`) endpoints with PyMongo.** FastAPI runs them in a threadpool and `MongoClient` is thread-safe and pooled, so concurrency is fine without Motor. Correctness under races comes from the database (unique index, conditional updates), not from Python locks.
- **`max(0, ...)` in the overtime helper.** Clamping negatives was fine; only the 30-minute rule was missing.
- **The helper split (late / work hours / overtime).** It's a good structure. I kept the functions but changed their signatures: they now take the employee and the attendance date, because shift instants depend on both.
